# Agents面经笔记

## Agents的定义/特征/组成

### 特征

- 自主性
- 循环执行

### 组成

- Brain/Core Engine
- Planning Module
  - LLM内置搜索能力
  - CoT机制
  - ReAct策略
  - 其他算法模块
- Memory Module
  - 长期记忆：经验/知识/用户偏好，通过检索（RAG）来为决策提供信息
  - 短期记忆：记录当前的对话历史/中间步骤思考过程等，维持拥护连贯性。
- Tool Use Module
  - 组成：外部API/函数库/硬件接口
  - 作用：扩展能力边界，比如执行代码，查数据库，用搜索引擎，甚至执行物理操作等

## ReAct框架

Reasoning and Act，一种循环模式，可以总结为“思考——行动——观察”的循环模式。

- Thought：分析当前任务和信息（Observation得来），然后生成**内心独白**，这就是Thought，这让Agent的行为变得可解释，有助于LLM自行形成规划/修正错误。
- Action：思考之后，LLM生成一个可执行的具体的行动。通常被格式化为`Action:[tool_name, tool_input]`的形式，input就是传给工具的参数。
- Observation：Agent的外部执行器（Harness）会解析LLM生成的Action，并实际调用对应工具。工具执行后的返回结果被格式化成**观察**信息反馈给LLM。它会作为新的上下文和原始目标一起输入到LLM中开始下一轮循环。

## ReAct结合CoT

传统CoT是一次性生成所有思考步骤，然后得到答案。但是ReAct的思考每一步行动前都会进行，所以是一个基于最新观察结果的思维链。

这样明显可以完成更复杂的规划，可以根据Tool返回的最新信息调整策略，并不断修正某些错误。

## 规划范式

### （基于提示）隐式规划

- CoT：最基础，线性的思考过程，一步到位，中间有错无法修正；
- ReAct + CoT：成为一个动态过程，每一步思考可以基于上一步观察重新规划，更有鲁棒性；

### （基于搜索）显式规划

- ToT（Tree of Thoughts）：从一个初始问题开始LLM会生成多个不同的并行的分支。最后采用树搜索算法（比如DFS/BFS），在每一步都对当前所有的节点进行评估（或者LLM自己打分），最后选择最又希望的节点进行下一步扩展。**允许模型探索/评估/回溯，能解决更复杂问题，但是计算开销大。**
- GoT（Graph）：允许不同分支Merge，允许循环，所以思维可以迭代地优化或精炼。**思维结构更加灵活，可以整合不同信息流或不断迭代的规划问题，但是结构更加复杂。**
- 拓展：CoMCTS（Collective MCTS），Mulberry论文。

### （基于任务分解）的规划

- LLM充当规划器，将任务显式分解，让另一个执行器来完成子任务。**结构清晰，易于管理进度；但是对分解能力要求很高，且可能缺乏较好的适应动态变化的能力。**

## Memory模块

### 短期记忆

存储当前任务的Context。比如对话历史/思考步骤/工具调用结果。

#### 实现方式

- LLM Context Window
- Buffer，比如LangChain就有不同类型的Buffer来管理对话历史：
  - <strong>ConversationBufferMemory:</strong> 存储完整的对话历史。
  - <strong>ConversationBufferWindowMemory:</strong> 只保留最近的K轮对话。
  - <strong>ConversationSummaryBufferMemory:</strong> 在历史对话过长时，动态地用LLM进行总结，以节省Token。
- Scratch Pad：记录ReAct框架的循环轨迹，便于逐步推理。

### 长期记忆

#### 检索方式

最主流的是使用RAG范式。

#### 存储技术

##### 向量数据库

1. 存储：Agent获得有价值的信息时会使用一个Embedding Model把文本信息转换成高维向量以映射键值对`<raw_text, vector>`的形式存储到向量数据库
2. 检索：在Agent进行规划的时候会把当前的任务/问题转换成一个Query，然后用这个Query到向量数据库里进行相似度检索，找出与当前情况最相关的历史记忆。
3. 使用：检索到的记忆/raw文本会被插入到LLM的Prompt中指导LLM进一步决策。

##### 其它

结构化/关系型数据库使用SQL或者图数据库进行存储和精确查询也可以。

## RAG

### 工作原理

- 检索：将问题作为一个Query发送给一个外部向量数据库搜索，找出相关信息；
- 增强：把检索得到结果和用户的原始问题拼接在一起，形成一个Augmented Prompt；
- 生成：把这个增强后的提示给LLM。LLM根据自身知识和Context生成更准确的更具有事实性的回答。

### 解决什么痛点

- **知识静态性和过时性**：RAG连接的外部DB可以随时更新；
- **Hallucination**：LLM回答知识范围外的知识时倾向于捏造事实；
- **缺乏专业领域知识/私有知识**：Fine-tuning也可以注入特定领域知识，但是成本高昂，知识有限；RAG可以让模型与私有数据集/知识库连接起来，更加灵活。

#### 与Fine Tuning相比优势在哪儿？

- 知识更新成本低；
- 可以追溯源文档，可解释性强，而fine tuning是黑盒子；
- 降低幻觉，RAG提供的依据可以追溯；
- 个性化程度高。

### 流程

1. 离线数据索引阶段
   - 数据加载
   - Chunk：加载进来的长文档切割成更小的、语义完整的文本块；
   - Embedding：用一个预训练Embedding Model，把每个文本块转换成一个高维数字向量。
   - Store：把每个文本块的内容和对应的嵌入向量存到向量数据库，数据库为向量建立索引。
2. 在线查询（推理）阶段：用户提出问题时实时执行。
   - 用户提问
   - Query Embedding
   - Retrieve（检索），进行相似度匹配，返回`top_k`个结果和对应原始文本块；
   - Rerank：引入重排序模型，把查询得到`top_k`个文本块进行更精细的打分和排序，进一步筛选。
   - Augment and Generate：重排序得出的几个文本块内容和用户原始问题一起，组合成一个增强提示发送给LLM。
