## 词法分析器（Lexer）
词法分析的输入是什么？
**CharStream + Token的规约。**
所以**有了一种Token规约，就可以设计一个词法分析器**。
有三种设计方法：
- 利用一个自动化的词法分析器生成器（比如利用ANTLR）；
- 手写词法分析器；
- 实现自动化词法分析器（相当于如何设计一个ANTLR？）
>生产环境下的编译器（gcc）更常用的是**手写词法分析器**。
>- 手写可能优化更好
>- 手写可以加入更多错误处理措施
>- 手写的工作量并不大
>但是**语法分析器**的工作量太大，所以一般不选择手写。

### 词法分析器生成器：ANTLR v4
![680](../../attachments/Pasted%20image%2020260512172802.png)
输入一个`.g4`格式的规约文件，ANTLR v4将文件名后加入`Lexer`字样，输出一个词法分析器文件（java格式）。
将`.c`文件交给这个分析器文件，就能生成一个Token流。
#### 词法分析器+语法分析器手写
>若要从头开始写代码，参考视频讲解。

视频中的代码版本无法处理形如`a=a+1;`的语句，这是因为**最长优先匹配原则**。等号后面会被解读成`a`和`+1`，而非`a` `+` `1`。
修改版本如下：
```g4
grammar SimpleExpr;

@header {
package simpleexpr;
}

prog : stat* EOF ;

stat : expr ';'
     | ID '=' expr ';'
     | 'print' expr ';'
     ;

/*
比如以上这个'print'，在输入的时候不会被识别为ID，虽然它符合识别ID的规则。
这是因为：print这种用单引号包裹起来的**字面量**，ANTLR v4会自动为其生成一个词法单元，会自成一类，它会把这些词法单元放在你自己
手动规定的词法单元前面。按照最前优先匹配规则，会先匹配print。
*/

expr : expr ('*' | '/') expr // 乘除的规则写在前面，来保证优先级比加减高；如果加减乘除在一个子规则里都写出（括号里），那么就无法区别优先级。
     | expr ('+' | '-') expr // 如果不明确写左/右结合，那就是默认左结合
     | ('+' | '-') expr
     | '(' expr ')'
     | ID
     | INT
     | FLOAT
     ;

/*
语法结构的描述放在前面（一般小写字母开头），词法结构的描述放在后面（一般是大写字母开头）
*/

SEMI : ';' ;
ASSIGN : '=' ;
PRINT : 'print' ;
MUL : '*' ;
DIV : '/' ;
ADD : '+' ;
SUB : '-' ;
LPAREN : '(' ;
RPAREN : ')' ; // 这几个可以使用 IntelliJ ANTLR v4插件右键Generate直接生成。

ID : ('_' | LETTER) WORD* ;
INT : '0' | [1-9]NUMBER* ; // 加?表示这个规则可以出现0次或者1次，也就是说正负号可以带可以不带。此处去掉了正负号的识别，让正负号被单独识别。
FLOAT : INT '.' NUMBER*
      | '.' NUMBER+
      ;

SL_COMMENT : '//' .*? '\n' -> skip ; // 字面量用单引号包裹。“.”是通配符，表示可以匹配任何除了换行符之外的任何字符。
// 同样应该让识别到的内容skip掉。
// 不加“?”，就是贪婪模式匹配，如果有多个换行符号，那么它会匹配到最后一个换行符为止。所以加上“?”变成非贪婪匹配
SL_COMMENT2 : '//' (~'\n')* '\n' -> skip ; // 这是另一种表达方式
DOCS_COMMENT : '/**' .*? '*/' -> skip ; // 把这个写在ML_COMMENT前面，是因为规则写在前面会被优先匹配，如果多行放在前面，会导致文档注释被识别成多行注释。
ML_COMMENT : '/*' .*? '*/' -> skip ;

WS : [ \t\r\n]+ -> skip ; // whitespace 对于空白符的识别 \r\n和\n是不同的换行形式，在Linux上和Windows上不同。
/* 而这里不能在列表后使用*，因为*表示>=0，而+才表示>=1个，如果用前者，那么没输入空白也会被识别为WS了。
设置-> skip是因为，为了避免在对源代码的词法分析的时候，输入的一个空白符被识别到，从而在语法分析阶段造成干扰。
（“a+b”和“a + b”在本例子中等价，但是如果不加->skip，就会导致后者识别时出错。）
*/

fragment LETTER : [a-zA-Z] ; // []是一种列表
fragment NUMBER : [0-9] ; // fragment是一种辅助的规则
fragment WORD : '_' | LETTER | NUMBER ;
//fragment OP : '+' | '-'; 后面定义的fragment对语法分析器不可见。
```
选择在前面的语法分析器中加入正负号的解析。
#### 冲突解决规则
![491](../../attachments/Pasted%20image%2020260514230311.png)
>最长优先匹配：如果同样的一个字符流可以被解读成一个合法的token或者一串更短的token，优先匹配那个长度最长的token（前者）。
>	> 比如`1.23`在示例中可以被解读成`1`和`.23`，但是由于前者长度更长，所以匹配前者。
